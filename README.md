# 英伟达黑客松十日谈｜一句话建电感，每一步都留证据

智研OS · SimEngineer：一个三人团队的仿真工程师 Agent 开发记录

队长：王诗涵｜团队：王诗涵、李世晓、刘佳伊

做了六年企业数字化转型，我却一直没想明白，自己的核心竞争力到底是什么。

研发、销售、采购、生产、检测，这些业务我都接触过。要列工作经历，能写不少；可真要回答“我最擅长什么”，我又有些说不清。做过的事多了，反而不容易找到一件自己愿意一直做下去、也确实能做好的事。

这个问题被我带进了清华自动化系。到了研二，我开始重新看过去那些项目。流程上线之后，很多专业工作依然卡在那里。仿真就是其中一项：要学建模，要设置边界条件，还得理解网格和求解器。业务工程师即使愿意学，也未必有足够的时间在项目周期内用起来。遇到具体问题，还是得等熟悉软件的专家，或者先按经验往下做。

我想试试，能不能让工程师把需求说出来，系统就帮他完成一部分专业软件操作。这样或许能少花些时间学界面、查操作，也能少等几轮任务交接。需要专家判断的地方，仍然留给专家。

带着这个想法，我们参加了英伟达黑客松。

## 三个人，从一句话开始

“帮我用 Ansys Maxwell 生成一个绕线电感模型，磁环内径5毫米，外径10毫米，高度5毫米，绕线5匝。”

这句话写下来只要几秒，我们却围绕它讨论了很久。

世晓先看出输入不完整，线径、材料和频率都没给，后面的建模与求解该按什么来？佳伊关心的是验证：“就算模型画出来了，怎么证明是按这句话画的？AI说‘通过’就可信吗？”

我惦记着最后的交付。工程师拿到结果以后，要能打开工程继续工作，知道用了什么参数，哪些假设还没确认。一张截图交不了这个差。

于是，范围收到了环形绕线电感上。完整的研发风险决策系统先放一放，这次先把一个具体任务从需求走到工程文件，再走到求解和报告。

分工也跟着清楚起来。我负责工程要求、产品规划和交付口径；世晓负责仿真 Agent 的架构和执行，把建模、求解、结果读取接起来；佳伊负责 AI 模型与软件集成，尤其是怎么检查模型的判断。我们各有负责的部分，也得把东西交到下一个人手里。

## 需求这件事，不能靠三个人各猜一遍

磁环的几个尺寸和匝数，足够让人理解要做什么。但真要往下建，导线线径、磁芯材料、绝缘要求还需要补齐。到了求解阶段，又要明确电流、频率等工作条件。

有些信息看起来已经给了，其实还不能直接用。比如“输入12V输出5V”，说的可能是电源电路指标，我们不能顺手把它当成电感的仿真激励。

我们把输入统一到同一份 `request.json` 里。每个字段除了数值，还要说明它从哪里来：用户确认过，还是检索到的候选值？允许系统调整，还是必须保持不变？没有确认的参数就继续问，不让 AI 自己选一个数，把后面整套计算带偏。

按这版方案，阶跃星辰模型负责需求整理和报告草稿，帮助抽取信息、组织文字。字段是否齐全、格式是否正确，由代码检查；需要工程判断的参数，仍要经过确认。

这也改变了我对演示的期待。以前总希望输入一句话，系统就一口气跑到底。现在碰到缺失信息，我反而希望它能明确停在哪一步，告诉用户还差什么。

## 世晓要交出来的，得是实际工程

“用 PyAEDT 调 Maxwell”，写在架构图上很短。世晓把它往下拆，工作就多了起来：创建工程、写参数、给对象命名、修改几何、启动求解，再处理失败和结果回读。

其中一件事我们反复强调：命令发出去了，还要回头看软件实际做了什么。计划里写了5匝，就检查实际绕组；脚本里有材料赋值，也要检查对象上的赋值状态。只检查准备发送的参数，发现不了执行时出了什么问题。

所以我们把交付要求写到了工程文件、实际参数状态和对象树上。进入求解以后，还要保存日志和结果数据。三视图是其中的一部分，不能替代这些文件。

佳伊也需要接住工程侧返回的状态。她原本负责 AI 代理模型、风险分级和模型服务化，这一版具体落在需求解析、视觉审查评估与系统集成上。世晓那边执行失败，模型这边就不能继续生成一段“已完成”的回答。哪一步完成了，哪一步还没完成，得在系统里分清楚。

## 先让视觉模型看真实的三视图

我们希望在求解之前加一道检查：结构有没有遗漏，部件是否错位，绕组有没有穿进磁芯。给 Agent 看三视图，是这次想验证的办法。

NVIDIA 的能力怎么接，我们考虑过两条线。一条是尝试用 TAO 的 `tao-generate-image-grounding` 做图像标注，辅助标出图中可见的磁芯、绕组，以及存在时的气隙、绝缘区，作为后续审查的输入。另一条是用 Cosmos 的视觉推理能力分析几何关系，把 `tao-finetune-cosmos-reason` 纳入基线评估和后续领域适配。面向具体任务的审查规则，则放在自定义的“三视图审查 Skill”里。

这些目前仍需要实际案例来验证。模型能描述一张图，离判断一个仿真工程能不能继续，还有距离。

测试的图片必须来自真实 Maxwell 工程。正视、俯视和侧视图要对应同一个版本，不能用重新生成的示意图替代。有些重叠只出现在投影里，有些部件被挡住了；遇到这类情况，就需要补充视角或几何证据。

佳伊负责的评估也因此要看失败样例：正常模型会不会被误报？遮挡时，模型会承认证据不足，还是硬给结论？审查输出除了“通过”，还要区分明确缺陷、需要补证据和需要人工审核的情况。这些问题都要测过，才能知道视觉审查是否帮上了忙。

## 返修时，谁能改什么

初版流程里，我画了一条返回箭头：有穿模，就退回去重画。

轮到写具体职责时，这条线就没那么简单了。首先得确认是真有干涉，还是图片看起来重叠。然后才是改哪个对象、改多少，以及有没有越过用户已经确认的要求。

5匝是明确要求，就不能为了消除干涉悄悄改成4匝。隐藏对象、换个角度重新截图，也没有修好工程里的问题。

我们把这段流程分开处理。我负责确定哪些需求不能动、哪些变量可以调整；佳伊把审查结果按证据分清楚；世晓根据允许的修改范围调整几何，保存新工程，再输出三视图重新审查。

改完之后，旧版本的“通过”就不能沿用了，旧求解结果也不能拿来解释新模型。返修次数和算力预算同样要设上限，超过预算或者问题仍然说不清，就交给工程师处理。

以前我画流程，更关注能不能连到下一步。这次开始关注每条线带过去的究竟是什么：一条建议，还是一个已经执行、可以检查的修改。

## “算完了”以后，还要检查什么

几何检查结束，后面还有材料、激励、边界、网格和求解设置。世晓负责的链路，需要把软件的实际状态读回来，包括求解成功还是失败、适用的收敛信息，以及结果能否正确提取。

我得先把“帮我分析一下”变成具体要求。用户要看电感、磁密、损耗，还是温升？看哪个区域、哪种工况？拿到指标后，要决定是否改设计，还是继续补验证？这些问题不先说明白，后处理就容易变成导出几张图交差。

佳伊负责检查结果进入模型和报告时有没有被改了意思。缺失值要保留为缺失，不能填成0；结果读取失败，就报告失败；没有实际计算依据的指标，标明“未评估”或“不可用”，并说明原因。

这些状态可能会让演示停下来，但读报告的人能知道自己手上的信息到哪一步了。

## DFMEA报告要能回到具体问题

DFMEA，也就是设计失效模式及影响分析，是智研OS原本就关注的方向。这次我们希望把它接到仿真后面，让报告中的问题能找到对应的工程版本、三视图、求解结果或人工审核记录。

比如建议调整线径，就要写清针对什么风险，允许改哪些变量，改完还要验证什么。只有一句“建议优化结构”，工程师拿到手里还是不知道该从哪里开始。

报告里还会遇到依据不够的地方。可靠性评分缺少适用方法，就保留“待评审”；某个失效判断缺少证据，也不能用一段流畅的解释补上。最终审核仍由承担相应职责的工程师完成。

我希望工程师看完报告，能据此安排下一轮修改或验证，也能分辨哪些建议现在还不能采用。

## 回到最初那个问题

十天，我们验证的不只是一条流程，也是一种协作方式：李世晓把架构里的动作落实成能执行、能验证的工程步骤；佳伊让 AI 输出能被测试、被接收，也在不可靠时被拦下来；我把每个交付对照到工程师真实要解决的问题。

我们都各有一段要负责，也都必须看见前后两段。

未来，智研OS还想走向厚膜电路、多物理场分析和更完整的研发风险决策。眼前，我们愿意先把这个电感做扎实：正常任务能完成，错误能被发现，证据不足时能停下来。

我们想做的，不是一个永远回答“可以”的 AI，而是一个知道何时继续、何时核查、何时请工程师一起判断的伙伴。

它需要遵守的那些原则——讲清输入、留下依据、承认未知、认真交接——也正是我们这个三人团队要继续做到的事。
